# 中文说明

这份文档是给仓库维护者、项目使用者和协作者看的中文入口说明。

它不替代模型执行时真正优先遵循的协议文件：

- `AGENTS.md`
- `.agents/common/rules.md`
- `.agents/common/context.md`
- 各类 workflow scripts
- 对应模型的 adapter prompt

换句话说：

- 这份文档主要帮助人理解这套仓库在做什么
- 真正让模型稳定执行的，仍然是英文优先的协议块和脚本

## 这套仓库解决什么问题

目标不是“收集一堆提示词”，而是把 AI 在真实项目里最容易失真的几个地方固定下来：

1. 身份边界不清
2. 项目上下文恢复不完整
3. 任务范围被模型偷偷扩大
4. 该先设计确认时直接开始 coding
5. 会话结束时只会口头总结，不会写进度和交接
6. 上下文太长时模型质量下降，却不先通知用户

所以这套仓库做的是三层东西：

1. 共享规则层
   约束模型怎么进入项目、怎么恢复上下文、怎么控制范围、怎么交接。

2. 项目地图层
   让模型知道“从哪读起”“哪些模块负责什么”“哪里还不确定”。

3. 记忆工作流层
   用脚本把 `progress.md`、`bugs.md`、`sessions/`、`decisions/` 真正写到文件里。

## 现在的核心约束

### 1. 身份优先

模型必须先确认 developer profile，才能读取个人目录。

即使用户在同一句话里同时说了：

- `使用 jake 身份`
- `并生成项目地图`

模型也必须先输出：

1. 当前 developer profile
2. 当前读写边界

然后才能继续做任务。

### 2. 先恢复，再行动

模型读完：

- `AGENTS.md`
- `.agents/common/rules.md`
- `.agents/common/context.md`
- `.agents/developers/{developer}/...`

之后，不能只说“我有上下文了”，而要显式回报：

- 当前 profile
- 读写边界
- 已读文件
- 当前进度
- 已知风险
- 下一步建议

### 3. 先设计，再确认，最后 coding

对 non-trivial 工作，默认流程是：

1. 先设计方案
2. 如果方案有非显然 tradeoff、会改生产代码、会扩大范围，就先问用户确认
3. 确认后再 coding

不能从设计讨论直接默默滑进实现。

### 4. 先声明 write scope

在 coding 前，要先说清楚预计会改哪些文件或模块。

如果真实改动范围超出了原先声明的范围，就必须停下来重新确认。

### 5. 不能静默扩大范围

例如：

- 用户只让你写测试
- 用户只让你补文档
- 用户只让你做验证
- 用户只让你修一个小点

都不代表你可以顺手：

- 改生产代码
- 做结构重构
- 做模块级 cleanup
- 改一堆相邻代码

### 6. 结束会话要真实落盘

结束一轮有意义的工作时，不应该只做自然语言总结。

默认要更新：

- `progress.md`
- 必要时 `bugs.md`
- `sessions/`
- 必要时 `decisions/`

如果仓库里有脚本，优先调用：

- `scripts/update-progress.sh`
- `scripts/append-session.sh`
- `scripts/append-bug.sh`
- `scripts/append-decision.sh`
- `scripts/close-session.sh`

### 7. 长上下文降级时不能擅自切换流程

如果模型觉得：

- 上下文已经太长
- 恢复质量下降
- 范围控制开始漂移
- 规则执行开始不稳定

它不能自己决定：

- 直接让用户重开会话
- 静默切到新线程
- 自己更换恢复策略

正确做法是：

1. 先通知用户质量风险
2. 说明建议的恢复动作
3. 先征得用户同意
4. 如果依赖当前会话记忆连续性，要明确提醒：先不要关闭当前会话

## 主要目录怎么理解

### `skills/shared/karpathy/`

这里放的是共享规则片段，主要负责：

- 项目级 `AGENTS` 规则
- 公共 `rules.md`

### `skills/shared/context/`

这里放项目地图模板，重点不是百科全书，而是：

- 从哪读起
- 模块怎么分
- 依赖怎么走
- 哪些地方还不确定

### `scripts/`

这里放真正能执行的脚本。

它们解决的是：

- 规则写了，但模型未必会真的写文件

所以用脚本把记忆层落盘。

### `docs/model-adapters/`

这里不是给每个模型重写一套规则，而是补一层轻量适配：

- 常见偏差
- 强提示词
- recovery 检查
- session-close 检查
- design-then-confirm 检查
- test-only boundary 检查
- scope-violation recovery 检查

目前已经覆盖：

- Cursor
- Qwen
- Codex
- Claude
- Gemini

## 推荐怎么用

### 新项目初始化

可以直接用：

```bash
./scripts/init-project.sh /path/to/project jake
```

它会一次完成：

- 公共规则注入
- 项目地图模板注入
- 开发者目录初始化

### 只初始化开发者目录

```bash
./scripts/bootstrap-developer.sh /path/to/project jake
```

### 会话结束时强制落盘

```bash
./scripts/close-session.sh /path/to/project jake ...
```

## 如果你要直接压模型

最常用的 3 类中文模板在这里已经有对应 guide：

1. 身份确认和任务同时出现时，先做 identity echo
2. 长上下文压力下，先通知并征得同意
3. 模型已经越界后，先按标准格式回报，不要长篇辩解

更具体的可复制模板，建议直接看：

- [Daily Workflow](daily-workflow.md)
- [How To Ask AI To Apply Skills](how-to-ask-ai-to-apply-skills.md)
- [Validate Agent Workflow](validate-agent-workflow.md)

## 一句话总结

这套仓库不是为了让模型“看起来更聪明”，而是为了让模型在真实项目里：

- 更少越界
- 更少脑补
- 更少漏写记忆
- 更稳定地按协议执行
